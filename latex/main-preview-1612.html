Extending Helm-DTN for Standalone OCI Image Transfer

Beginner-Oriented Design and Code Walkthrough

Implementation report — 5 August 2026

Abstract

This report explains how the original Helm-DTN project works, why its normal chart-based pipeline cannot directly satisfy the requirement to provision a remote registry before Kubernetes exists, and how the new Go implementation adds standalone OCI-image transfer over the existing AAP2/μD3TN path. Every important claim is connected to the current repository file and line range. The intended endpoint is an OCI registry such as Harbor on the Space side. Kubernetes is deliberately not required by the transfer stage; once the registry contains the images, Kubernetes/containerd can pull them normally.

The requirement in plain language

The system must move a real container image such as docker.io/library/nginx:alpine, not merely a YAML reference to that image. It must work without inventing a Helm chart, use the existing Go AAP2 client to cross the delay-tolerant network, place the received OCI content in the configured Space-side Harbor/OCI registry, and verify that the destination digest equals the source digest.

The boundary matters: this implementation ends at a usable registry. It does not run kubectl, create a Pod, or assume that Kubernetes already exists. That is necessary for provisioning use cases: Talos and Kubernetes images have to arrive before the cluster can consume them.

Helm and the original Helm-DTN code

What Helm actually does

Helm is a Kubernetes package manager. A chart contains templates and values; Helm renders these into Kubernetes objects and asks the Kubernetes API to install them. An image field in a Deployment is only a string such as nginx:alpine. Helm does not copy the image layers. After the Pod is scheduled, the node's container runtime pulls those layers from a registry.

Therefore ``Helm cannot transfer a standalone image'' should be understood as a responsibility boundary, not a defect in Helm. Helm manages releases and manifests. OCI registries and container runtimes manage image manifests, configurations, and layer blobs.

How the supplied Helm-DTN pipeline is chart-coupled

The original project adds image packaging around Helm charts:
  1. pkg/helmdd/helmdd.go renders a chart and discovers image strings from generated Kubernetes manifests.
  2. pkg/helmdl/helmdl.go downloads the discovered images.
  3. pkg/helmdp/helmdp.go packages the chart and image archives for transport.
  4. pkg/helmdtnt/receiver.go receives the deployment, loads/pushes images, and invokes Helm install or upgrade.

The clearest evidence of the receiver's cluster dependency is pkg/helmdtnt/receiver.go, lines 170--182, where the command type leads to installChart, upgradeChart, or uninstallChart. The actual Helm installation is at lines 278--303. At lines 351--370, Helm initializes a Kubernetes action configuration and loads a chart from a local path. This is correct for chart deployment, but it assumes both a chart and a Kubernetes target.

The image loading part is similarly embedded in that deployment handler: pkg/helmdtnt/receiver.go, lines 212--239, reads files from an Images directory, constructs registry references, reads tarballs, and pushes them. There is no independently addressable ``send this OCI image'' command.

Why a fake chart is the wrong workaround

A dummy chart could contain a Pod referring to an image, thereby causing the existing detector to notice it. However, this would add an artificial chart, trigger chart rewriting and Helm release behavior, require Kubernetes on the receiver, and confuse registry provisioning with workload deployment. It also makes failure recovery operate at the wrong abstraction: the desired unit is an image, not a Helm release.

New architecture

The extension creates an explicit image path while retaining the existing AAP2 transport:

Source registry $→$ Go sender $→$ OCI-layout TAR $→$ one AAP2 ADU $→$ μD3TN $→$ Go receiver $→$ Harbor/OCI registry.

Sender: exact code path and reasons

Inputs

In cmd/image-sender/main.go, lines 27--37, repeated -image and -registry-target options support one or many explicit mappings. The -images-file option supports a reproducible list. The -os and -arch options are needed because many registry tags point to a multi-platform index; a provisioning transfer must select the platform that the Space machines will execute.

At lines 38--48, the sender rejects missing network parameters and delegates request construction to imageplan.Build. Centralizing parsing prevents the sender and verifier from interpreting the same list differently.

Temporary storage and AAP2 reuse

At lines 51--66, the sender creates a temporary working directory when the caller does not provide one and removes it on exit. Images may be hundreds of megabytes, so using files prevents the entire payload from being retained as a Go byte slice.

At lines 67--74, the code creates the project's existing AAP2TCPClient, connects, and registers agent go-image-sender. This is the key minimal-change decision: DTN routing, framing, and compatibility continue to use the supplied AAP2 implementation. No parallel DTN library or protocol was introduced.

One image per ADU

The loop at lines 75--102 implements the transfer lifecycle. At \line79, ExportOCI pulls the image. At lines 83--87, the destination name is stored in the header and the payload file is built. At lines 88--94, the whole framed payload is submitted as one AAP2 Application Data Unit (ADU) and the sender waits for the local acceptance response.

This code does not implement application-level chunking. One image is one ADU. Internally, Go's io.Copy streams bytes in bounded buffers, and Bundle Protocol/μD3TN may fragment or transport data underneath, but there is no numbered-chunk protocol or reassembly table in this application. That distinction is important when diagnosing contact-capacity failures.

OCI export and payload format

External libraries actually used

The direct dependencies are recorded in go.mod. The relevant lines are: github.com/google/go-containerregistry v0.20.7 at \line6 and github.com/google/uuid v1.6.0 at \line7.

go-containerregistry supplies registry authentication, reference parsing, platform-aware pulling, OCI layout operations, and pushing. It avoids a Docker daemon and avoids shelling out to Skopeo. google/uuid creates a unique transfer identifier. Standard-library packages such as archive/tar, crypto/sha256, encoding/json, and io are not third-party libraries. Existing project dependencies provide AAP2 protobuf messages and networking.

Header and limits

pkg/imagetransfer/transfer.go, lines 25--38, defines a 1 MiB maximum header, a 64 GiB maximum archive, and the metadata fields: transfer ID, source, target, creation time, source digest, archive SHA-256, and archive size. Explicit bounds prevent malformed or hostile input from causing unbounded allocation or disk consumption.

At lines 40--55, ValidateTarget rejects URLs, absolute paths, empty components, and dot traversal. This is required because a sender-controlled target is appended to the receiver's trusted registry prefix. Without this check, input could attempt to escape that namespace or redirect a push.

At lines 57--70, DefaultTarget derives a destination repository and tag when possible. Digest-only source references require an explicit target because a destination push needs a usable repository name and tag/digest mapping rather than an ambiguous default.

Pulling a real image into an OCI layout

At lines 72--109, ExportOCI parses the source and calls remote.Image with keychain authentication and the selected platform (lines 75--85). It creates an OCI image layout at lines 88--99, appends the image, turns the layout directory into a TAR at \line100, and hashes the TAR at lines 104--108. The result is a standards-based OCI object containing the manifest, configuration, and layer blobs—not a text reference.

Wire framing

At lines 111--150, CreatePayload writes exactly: 
[8-byte unsigned big-endian JSON length][JSON Header][OCI-layout TAR bytes]
The length prefix lets the receiver know where metadata ends and binary image data begins. The JSON is readable and versionable; the TAR remains streamable. At \line142, io.Copy copies file-to-file rather than loading the archive into memory.

Integrity checks on Space

At pkg/imagetransfer/transfer.go, lines 152--205, DecodePayload reads the bounded header exactly, checks all required fields, validates the target and archive size, extracts only the declared number of bytes, and recomputes size and SHA-256. Corruption or truncation is rejected before any registry push.

The source manifest digest and archive checksum serve different purposes. The archive checksum proves transport-byte integrity. The manifest digest proves that the registry-visible image content is the same image, even though registry storage need not preserve the surrounding TAR byte-for-byte.

AAP2 client modification

The extension intentionally makes a small change to pkg/aap2_client/aap2_sync_client.go. The existing SendFile path at lines 238--260 is reused. Its new size check is at lines 245--251; streaming to the connection remains at lines 252--258. This avoids announcing one length and streaming another.

The in-memory receive paths use io.ReadFull at lines 78--85 and lines 162--168, ensuring a short TCP read is not mistakenly treated as a complete payload. The new ReceiveAduFile method at lines 171--197 streams exactly PayloadLength bytes to a file using io.CopyN at \line188. This is necessary because normal network reads are allowed to return fewer bytes than requested and because provisioning images should not require an equally large RAM allocation.

These are transport-hardening changes, not a replacement for AAP2. The sender and receiver still configure, send messages, send response statuses, and carry ADUs through the original Go client.

Receiver: from DTN to Harbor

In cmd/image-receiver/main.go, lines 17--24 define the Space AAP2 address, subscriber agent ID, optional secret, registry prefix, work directory, and a testing-only insecure-registry switch. Harbor credentials are read at lines 29--40 from REGISTRY_CREDS; HARBOR_CREDS is supported for backward compatibility. No value means anonymous registry access.

The outer loop at lines 44--49 reconnects after an AAP2 failure. DTN links and long-running nodes can be intermittent, so a receiver must not exit forever on one lost TCP connection.

At lines 52--65, the receiver uses the existing AAP2 TCP client and subscribes as image-transfer. At lines 66--87, it receives the ADU metadata, acknowledges the AAP2 message, streams the declared payload into a unique file, processes it, and removes the temporary payload.

At lines 90--104, handle decodes and verifies the payload, combines the administrator-controlled registry prefix with the validated relative target, pushes the OCI image, and logs its verified digest. There is no Helm install and no Kubernetes client in this executable.

Registry push and end-to-end verification

PushOCI in pkg/imagetransfer/transfer.go, lines 208--260, safely expands the OCI layout, opens the image, parses the destination reference, selects basic or anonymous authentication, and writes it through the Registry V2 API. After the write it calls remote.Head and compares the registry's reported digest with the local image digest. A successful HTTP upload alone is insufficient; the read-back proves that the expected manifest is addressable at the target.

The separate program cmd/image-verify/main.go provides independent acceptance evidence. At lines 28--33 it loads the same validated mapping and credentials. At lines 34--54 it calculates the selected-platform source digest, calculates the remote target digest, compares them, and prints OK only on equality. Any failure causes a non-zero process exit at lines 55--57. The digest helper at lines 75--100 deliberately uses source keychain authentication and destination registry credentials separately.

Image-list methodology

pkg/imageplan/plan.go, lines 17--98, accepts either command-line pairs or a text file. Each non-comment line is either SOURCE or SOURCE=TARGET. It rejects missing sources, mismatched repeated options, malformed mappings, unsafe targets, and an empty final plan. This shared package makes batch transfers reproducible and keeps validation identical between transfer and verification.

Two examples are supplied. examples/kubernetes-images.txt is a small demonstration. examples/talos-v1.13.6-kubernetes-v1.36.2-images.txt is a pinned provisioning set. Pinning versions is necessary because a mutable ``latest'' set makes results and future incident analysis irreproducible.

Local acceptance script and DTN capacity

scripts/run-local-acceptance.sh, lines 4--11, selects the image list, registry, Earth and Space AAP2 endpoints, destination EID, contact duration, and contact rate. At lines 19--23, it starts the existing test containers and configures the Earth-to-Space contact. The default rate is 10,000,000 bytes/s for 3,600 seconds, giving about 36 GB of scheduled capacity.

This setting was needed because the earlier 100,000 bytes/s contact offered only about 360 MB total. Several Talos images individually approach or exceed that practical budget once bundle overhead and multiple images are considered; μD3TN consequently reported insufficient contact payload capacity. This was a DTN scheduling capacity issue, not an OCI or Harbor failure.

At lines 25--34, the script starts the receiver and sender. At lines 36--48, it waits for the expected number of registry pushes rather than assuming local AAP2 acceptance means remote delivery. Finally, at lines 50--55, it runs independent digest verification and reports completion.

Security, reliability, and limitations

  • Integrity is checked with archive SHA-256 before pushing and manifest digest after pushing. This detects corruption; it is not a digital signature. For hostile environments, add signed transfer metadata or verify Cosign/OCI signatures against a trusted policy.
  • -insecure-registry permits HTTP and must remain limited to local testing. Real Harbor should use TLS and appropriately scoped robot credentials.
  • Credentials are currently passed as user:password in an environment variable. A colon in the username is unsupported, and environment visibility may be undesirable. A secret file or credential helper is a future hardening improvement.
  • One image equals one ADU. There is no application retry ledger, resumable-chunk protocol, deduplication across images, or garbage-collection policy for failed receiver files.
  • Sender acceptance confirms that local μD3TN accepted the ADU; it does not itself confirm remote Harbor completion. Receiver logs and image-verify provide that evidence.
  • A local Registry V2 endpoint has been used for functional validation. The same API is used by Harbor, but final deployment should still test actual Harbor TLS, project permissions, quotas, and retention rules.

How to build and run

Build the three programs from the repository root: 
go build -o bin/image-transfer-send ./cmd/image-sender
go build -o bin/image-transfer-receive ./cmd/image-receiver
go build -o bin/image-transfer-verify ./cmd/image-verify

On Space, start the receiver (use TLS in production): 

export REGISTRY_CREDS='robot-user:password' bin/image-transfer-receive \   -tcp 127.0.0.1:4242 \   -registry harbor.space.example/provisioning

On Earth, send one real image: 

bin/image-transfer-send \   -tcp 127.0.0.1:4242 \   -destination-eid dtn://space.dtn/image-transfer \   -image docker.io/library/nginx:alpine \   -registry-target library/nginx:alpine \   -os linux -arch amd64

After delivery, verify the batch with image-transfer-verify. Kubernetes can then refer to the transferred image. The optional fifth-step script is: 

IMAGE='harbor.space.example/provisioning/library/nginx@sha256:<digest>' \ EXPECTED_DIGEST='sha256:<digest>' KUBE_CONTEXT='space-cluster' \ PROBE_MODE=http scripts/run-kubernetes-image-acceptance.sh
This Pod test is a consumer of the DTN result rather than part of the transport itself, so it remains independently runnable.

Optional fifth step: Kubernetes pull and start proof

scripts/run-kubernetes-image-acceptance.sh, lines 6--37, validates the image, SHA-256 digest, object names, probe mode, kubectl, and optional context. Requiring a digest is important: a successful pull of a mutable tag would not prove that Kubernetes used the same image verified in step four.

At lines 39--66, the script checks API readiness, creates an isolated namespace, optionally creates a registry pull secret from REGISTRY_CREDS, and selects either ordinary container readiness or an HTTP readiness probe. At lines 68--85, it replaces the proof Pod and sets imagePullPolicy: Always, preventing a previously cached tag from making the test pass without contacting the registry.

At lines 94--102, it waits for the Pod to be Ready and collects diagnostics on failure. At lines 104--118, success requires all three facts: phase is Running, container readiness is true, and the runtime's status.containerStatuses[0].imageID contains the exact expected digest. Only then does it print KUBERNETES_IMAGE_ACCEPTANCE=PASS.

The script has passed Bash syntax validation. A live attempt reached the Pod and produced ErrImagePull because the disposable kind node could not resolve the local registry container through WSL DNS. The retained kind control plane then stopped with Docker exit code 128, and a replacement node failed during system startup. Therefore the fifth step is implemented but has not yet produced a passing live result in the currently unstable local Docker/WSL environment. This must not be reported as a successful Kubernetes acceptance until the script emits its explicit PASS record.

Testing status and honest completion boundary

Unit tests cover the newly introduced parsing, framing, integrity, target validation, and exact AAP2 file I/O. A real registry.k8s.io/pause:3.10 image was transferred through the local DTN test environment into a Registry V2 destination and verified at digest sha256:7c38f24774e3cbd906d2d33c38354ccf787635581c122965132c9bd309754d4a.

The full pinned 17-image Talos acceptance run has not yet completed in one uninterrupted execution, and a real Space Harbor has not yet been exercised. Consequently, the implementation is present and the core path is demonstrated, but final acceptance should require: go test ./..., one uninterrupted 17/17 run, independent 17/17 digest verification, and a deployment-environment Harbor test.

Beginner's mental model

Keep four acknowledgements separate:
  1. The source registry returned a valid image and digest.
  2. Earth μD3TN accepted the image ADU locally.
  3. Space received, checksum-validated, and pushed the OCI image.
  4. A fresh registry read returned the same manifest digest.
The fourth statement establishes the standalone transfer result. The optional fifth statement tests Kubernetes integration using the separate acceptance script. It deliberately remains outside the supervisor's standalone provisioning-image transfer boundary, even though the repository now supports running it when a healthy cluster is available.
